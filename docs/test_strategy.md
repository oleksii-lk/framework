# E2E demo-stand 

## Опис проєкту
Демонстраційний проєкт реалізує спрощений сервіс, що надає користувачу можливість авторизуватись, 
переглянути інформацію про поточного користувача, та завершити сесію. 
Проєкт складається з 3-х частин: 
- Фронтенд: Typescript, React 
- Бекенд: Python, fastapi, unicorm
- E2E тести: Typescript + playwright

Проєкт організований як mono-репозиторій, що має свої як переваги так і недоліки.

Мета проєкту: продемонструвати підходи до стратегії автоматизованого тестування web-застосунку.    

## Стратегія тестування
### Підхід до вибору стратегії
Приймемо за основу наступну ієрархію автоматизованих тестів: Unit -> Component -> Integration -> End-to-End.   
Чим вище рівень тестів, тим дорожче їх як виконання (час виконання та можлива нестабільність роботи), так і розробка
(час на імплементацію та підтримку). 
   
Основний підхід до забезпечення тестового покриття це використовувати тести вищого рівня тільки тоді, 
коли неможливо гарантувати репрезентативність тестів нижчих рівнів.   

Правило для само-перевірки:   
Чи можливий сценарій, за яким E2E тести знайдуть помилку при успішному виконанні Unit/Integration тестів?
Чи можливо знайти цю помилку тестами рівнем нижче? 

### Вибір інструментів
#### Backend Unit/integration tests
- `Pytest`: де-факто галузевий стандарт
- `fastapi`: fastapi.TestClient надає зручні інструменти для тестування та емуляції http запитів, без фактичного створення сесії.
Поширені web-фреймворки надають інструменти тестування, то ж вирішальним вибором можуть бути інструменти що вже задіяні на проєкті.   

#### Frontend Unit/Component tests
- `testing-library/react` та інші: де-факто галузевий стандарт для React застосунків
- `vite`: вирішальними факторами для вибору були простота налаштування та швидкість роботи в порівнянні з Jest 

#### Frontend E2E tests
- `TypeScript` як мова програмування
  - TypeScript обраний через строгу типізацію, що спрощує підтримку тестів з ростом проєкту
  - E2E тести найбільше взаємодіють з web-інтерфейсом. Це теж фактор на користь TypeScript, 
    що забезпечить одноманітність кодової бази та зменшує когнітивне навантаження 
- `Playwright` як тестовий фреймворк 
  - Швидкість роботи вища чим в інших фреймворків, таких як Selenium чи Cypress, що може бути критичним при великому обсягу тестів 
  - Простий в налаштуванні та розробці, має вбудовані інструменти для пошуку та очікування веб-елементів 
  - Підтримує паралельне виконання і не потребує для цього розгортання додаткової інфраструктури (Selenium Grid) чи сторонніх сервісів (як то Cypress cloud)

### E2E Тестове покриття 
Враховуючи обраний підхід, E2E тести використовуються для 
перевірки загального успішного шляху, а також сценаріїв що потребують переходу між сторінками, та залежать від стану внутрішнього сховища браузера. 
Це те що інструменти рівня Unit/Integration тестів можуть емулювати, але не відтворити в точності.   

Валідація web-сторінок, відповідність тексту повідомлень до ситуації, чи сценарії з токеном авторизації тестуються на рівні Unit/Integration тестів.

Тести на валідацію вводу (наприклад на захист від SQL Injection) не реалізовані. Проєкт демонстраційний та не має бази даних.
При необхідності, вони будуть імплементовані на рівнях: 
- Unit tests - валідація вхідних даних
- Integration - валідація api запитів

Сторінки:
- Home page "/" - домашня сторінка, доступна публічно
- Dashboard "/dashboard" - інформація про користувача, доступна авторизованим користувачам
- Not-found - на випадок невірної відносної URL, доступна публічно
- Login "/login" - сторінка авторизації

| Група     | Сценарій | Призначення                                                                  |
|-----------|----------|------------------------------------------------------------------------------|
| Login     | logs in and redirects to dashboard | Загальний успішний шляхвходу в систему                                       |
| Login     | shows an error and stays on the login page for wrong credentials | Загальний негативний шлях                                                    |
| Login     | redirects unauthenticated users from /dashboard to home | Перевірка переходу для не-авторизованих користувачів                         |
| Login     | logging out from the dashboard returns to home | Загальний успішний шлях виходу з системи                                     |
| Dashboard | logout redirects to home | Не має практичної цінності, наведений для демонстрації beforeEach            |
| Home      | shows dashboard link and logout button when authenticated | Не має практичнох цінності, наведений для демонстрації авторизації через API |
| Not-found | Route to 404 page for an unknown route | Негативний шлях на випадок некоректної адреси                                |

#### Підсумки
- На рівні E2E тести перевіряють 5 сценаріїв, з них 3 позитивних і 2 негативних
- E2E доповнюють Unit/Integration тести, але не заміняють їх, що скорочує час на розробку, та пришвидшує CI

## CI/CD Автоматизація запуску тестів та розгортання
Наразі на проєкті не реалізована система управління версіями, і відсутні середовища для розгортання.    
Це задачі специфічні до технічних особливостей та залежать від цілей проєкту.   

Один з можливих процесів:

```
Pull Request opened / updated
│
├─► Unit & integration tests
│     └─ static analysis / quality gates
│
├─► Provision preview environment
│
├─► E2E tests 
│
└─► PR ready to merge

Merge to main
│
├─► Unit & integration tests
│
├─► Deploy staging
│
├─► E2E tests against staging
│
├─► Release
│
├─► Manual approval gate
│                    │
│              approved │ rejected
│                    │        └─► stop
│
└─► Propagate staging build to production
```

| Trigger        | Tests          | Environment | Gate            |
|----------------|----------------|-------------|-----------------|
| [Pull request](../.github/workflows/pull-request.yaml) | unit + e2e     | preview     | all green       |
| Push to main   | unit + e2e     | staging     | all green       |
| Staging passes | —              | production  | manual approval |

Виконання E2E тестів на Production середовищі повʼязане з ризиками засмічення та/або пошкодження даних,
хибних нотифікацій, і небажаних подій у випадку інтеграції з сторонніми системами (наприклад billing). 
Для моніторингу стану production систем бажано використовувати спеціалізовані системи.
